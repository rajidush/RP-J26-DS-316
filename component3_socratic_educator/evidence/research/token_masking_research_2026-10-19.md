# Finite-automaton token masking: the mechanism and Component 3's implementation

Research date: 19 October 2026. Scope: the masking mechanism itself, checked against primary sources, and how [src/token_mask.py](../src/token_mask.py) relates to them. The child-facing LM Studio path (JSON schema, post-check, fallback) is covered in [grammar_decoding_research_2026-10-18.md](grammar_decoding_research_2026-10-18.md) and is not repeated here. Sources were downloaded and read on the research date: five arXiv PDFs, llama.cpp pinned to commit [`ff5a233`](https://github.com/ggml-org/llama.cpp/tree/ff5a23376725e5a889fa0bfb987b7541dc304da0) (master on 19 Oct 2026), and transformers at tag [`v4.53.2`](https://github.com/huggingface/transformers/tree/v4.53.2), the version recorded in the [run record](token_masking_2026-10-18/token_masking_2026-10-18.run_record.json). No repo file other than this note was changed. `tests/test_token_mask.py` was run: 27 passed.

## What to say to the panel

> A language model chooses every token from a probability distribution over its whole vocabulary (262,144 tokens for Gemma 3), so a prompt cannot stop it picking a token that breaks the format, and a check afterwards can only reject the finished line. I wrote the INTERCEPT line's grammar as a finite automaton over characters. Before each token, my code works out which vocabulary tokens keep the automaton alive through every one of their characters, and it allows end-of-generation only once the line is complete. Every other token's score is set to minus infinity before the model chooses, so those tokens cannot be picked: on gemma-3-1B the unmasked line failed the grammar, the masked line passed, and the model's first choice was blocked at 8 of 26 steps. This guarantees structure, not meaning, so the post-check and the fallback line stay in place; the child-facing path uses the same idea inside LM Studio's llama.cpp engine, which uses a pushdown automaton because JSON in general needs a stack, whereas my one-line grammar needs only a finite automaton.

## 1. Why masking is needed

- **The model samples from the whole vocabulary.** Willard & Louf define the next token as `s_{t+1} ~ Categorical(α)` with `α = LLM(S_t, θ)`, `α ∈ R^N`, over a vocabulary whose size N "is often on the order of 10^4 or larger" ([Outlines paper, §2](https://arxiv.org/abs/2307.09702)). XGrammar describes the same pipeline: the model "produces a logits vector across its vocabulary, which is then converted into a probability distribution using the softmax function", and "a sampler then selects the next token" ([XGrammar, §2.1](https://arxiv.org/abs/2411.15100)). Softmax gives every finite logit a probability above zero, so any token can be sampled. (That last step is the definition of softmax, not a quoted claim.) Under greedy decoding the top token is taken. In the 18 Oct trace, step 0's top token was `"Okay"` at p = 0.74, which already rules out both openers ([summary](token_masking_2026-10-18/token_masking_2026-10-18.summary.md)).
- **Prompting and fine-tuning do not guarantee format.** Guided generation exists "to make LLM model output usable under rigid formatting requirements that are either hard or costly to capture through fine-tuning alone" ([Outlines, §1](https://arxiv.org/abs/2307.09702)). Geng et al. say LMs "still struggle with reliably generating complex output structures when not finetuned to follow the required output format exactly", and they present grammar-constrained decoding as "guaranteeing that the output follows a given structure" ([Geng et al., abstract](https://arxiv.org/abs/2305.13971)). llama.cpp keeps the two channels apart: a JSON schema "is only used to constrain the model output and is not injected into the prompt" ([GBNF guide, L151](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/grammars/README.md?plain=1#L151)). The prompt describes the format and the mask enforces it.
- **Post-hoc validation can only reject.** Rejection sampling "repeatedly samples strings from the LLM and checks them against a validity oracle" and is "highly inefficient or simply intractable for restrictive grammars and long output sequences" ([Park et al., Grammar-Aligned Decoding, §1](https://arxiv.org/abs/2405.21047)). Constrained decoding "reduces the need for ad-hoc parsing, retrying and prompting" ([Beurer-Kellner et al., DOMINO, §1](https://arxiv.org/abs/2403.06988)). Component 3's post-check has no retry loop: a rejected line becomes the fallback line ([grammar_decoder.py `_intercept`](../src/grammar_decoder.py)). The unmasked trace line, "Okay, let’s talk about what you were doing on your screen just now.", is an example of exactly what that path would throw away.

## 2. How it works

1. **Grammar to finite automaton.** Outlines expresses a regular expression as a 5-tuple finite automaton `(Q, Σ, δ, q0, F)`: states, alphabet, transition function, start state and accept states ([Outlines, Definition 1](https://arxiv.org/abs/2307.09702)). The student's `InterceptAutomaton` has a start state, a `step` transition function that returns `None` for "no valid line continues this way", and an `is_accepting` test for the single accept state `("end",)`. By breadth-first search over printable characters, it has **193 reachable live states**: opener prefixes, the gap before the question, question positions 0–99, and end.
2. **Tokens are multi-character strings.** In Outlines, "the characters comprising the strings in V are drawn from Σ". Algorithm 3 walks the automaton through every character of a vocabulary string and gives up on a start state as soon as `δ(r, v_i)` is undefined ([Outlines, §3, Algorithm 3](https://arxiv.org/abs/2307.09702)). XGrammar names the hard part: each token "comprises multiple characters, which may cross the boundaries of grammar elements" ([XGrammar, §1](https://arxiv.org/abs/2411.15100)). In the student's code, `TokenMask.allowed` keeps a token only if `automaton.run(text, state)` survives every character. The test `test_a_token_may_span_the_opener_and_the_question` checks that `" What"` (the gap's space plus the question's capital) is allowed and `" what"` is not.
3. **Mask the scores before choosing.** Outlines applies a boolean mask `m` that "restricts the support of the original distribution", `α̃ = m ⊙ α`, at the step before sampling ([Outlines, §2.2, Algorithm 2](https://arxiv.org/abs/2307.09702)). XGrammar: invalid tokens' "logits are set to −∞, effectively assigning them zero probability after the softmax operation and preserving the relative probabilities of other valid tokens" ([XGrammar, §2.1](https://arxiv.org/abs/2411.15100)). In transformers 4.53.2, `generate` runs `next_token_scores = logits_processor(input_ids, next_token_logits)` and then takes either `argmax` or `softmax` plus `multinomial` ([utils.py L3625–L3653](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/utils.py#L3625-L3653)), so a processor's `-inf` takes effect before either decoding mode.
4. **End-of-sequence only in an accepting state.** Outlines defines the target outputs as token sequences "that end with a special token EOS" ([§2.1](https://arxiv.org/abs/2307.09702)). llama.cpp sets an end-of-generation token's logit to `-INFINITY` unless some grammar stack is empty, meaning the grammar is complete ([llama-grammar.cpp L1359–L1400](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L1359-L1400)). It aborts if one is accepted anyway ([L1449–L1456](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L1449-L1456)). `TokenMask.allowed` adds `end_ids` only when `is_accepting(state)`. After the `?`, nothing else survives, so the trace's last step allows exactly the 2 end tokens.
5. **Per-step cost and the Outlines index.** The common approach evaluates the whole vocabulary each step, "a fixed O(N) cost for each token generated", and re-matching from the start of the sequence adds "a cost that grows at least linearly" ([Outlines, §1, §2.2](https://arxiv.org/abs/2307.09702)). Outlines instead tracks the automaton state between tokens, "without reading from the beginning of the growing sample sequence each time". It also builds, before generation, a map `σ: Q → P(V)` from each state to the tokens accepted from that state, by running Algorithm 3 from every state (Algorithm 4). With a hash map, the mask step costs "O(1) on average", and the index is "constructed outside of the token sampling procedure" ([§3](https://arxiv.org/abs/2307.09702)).

## 3. How three real systems do it

| System | Automaton | When the allowed set is computed | How tokens are masked |
|---|---|---|---|
| Outlines (paper) | Finite automaton for regex. CFGs via LALR(1) parser plus PDA ([§4](https://arxiv.org/abs/2307.09702)) | Precomputed index `σ` per state | Boolean mask on the distribution |
| llama.cpp GBNF | Grammar over Unicode code points, run as a set of pushdown stacks | Every step, over the candidate tokens | Logit set to `-INFINITY` |
| transformers | None built in for regex. You supply a `LogitsProcessor` | Whatever the processor does | Processor returns modified scores |

**Outlines.** The abstract claims the approach "adds little overhead" and "significantly outperforms existing solutions". The paper shows this with a single-sample timing comparison against Guidance, which at the time applied partial regex matching "from the start of the sampled sequence each time" and iterated over the vocabulary (N = 50,257) on each step ([§3.2](https://arxiv.org/abs/2307.09702)). The paper reports a naively built index for a Python grammar of "around 50 MB" ([§5](https://arxiv.org/abs/2307.09702)).

**llama.cpp.** GBNF terminals are "characters, specifically Unicode code points". The grammar supports `{m,n}` repetition ([GBNF guide L11, L62–L68](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/grammars/README.md?plain=1#L11)). llama.cpp converts "a subset" of JSON Schema to GBNF, including through the `/chat/completions` `response_format` field. "Unsupported features are skipped silently", and patterns "must start with `^` and end with `$`" ([L141–L212](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/grammars/README.md?plain=1#L141-L212)). In the source, `llama_grammar_advance_stack` "transforms a grammar pushdown stack into N possible stacks" ([L858](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L858)). `llama_grammar_reject_candidates_for_stack` matches every candidate's first code point against the stack top, keeps the survivors, advances the stack, and recurses on their next code point ([L1061–L1130](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L1061-L1130)). Tokens that split a UTF-8 character are tracked with `partial_utf8`, and empty pieces get `-INFINITY` ([L1359–L1400](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L1359-L1400)). In the code I read, nothing is precomputed per state: the check runs at every step.

**transformers 4.53.2.** The v4.53.2 docs say "a LogitsProcessor can be used to modify the prediction scores of a language model head for generation" ([generation utilities docs](https://huggingface.co/docs/transformers/v4.53.2/en/internal/generation_utils)). `LogitsProcessor` is the "abstract base class for all logit processors". Its `__call__(input_ids, scores)` takes scores of shape `(batch_size, config.vocab_size)` and returns "the processed prediction scores" ([logits_process.py L36–L57](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/logits_process.py#L36-L57)). `generate(logits_processor=...)` accepts "custom logits processors that complement the default logits processors" ([utils.py L2282–L2285](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/utils.py#L2282-L2285)). The built-in `PrefixConstrainedLogitsProcessor` takes an allowed-token function, builds `torch.full_like(scores, -math.inf)`, sets allowed positions to 0 and adds the mask to the scores ([L1329–L1397](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/logits_process.py#L1329-L1397)). That is the same operation as `MaskingLogitsProcessor`.

**Newer work (read).**
- XGrammar splits the vocabulary into "context-independent tokens that can be prechecked" and context-dependent tokens checked at runtime. These are "less than 1% (1134 out of 128k)" for Llama-3.1 on JSON. It reports "up to 100x reduction in per-token latency for context-free grammar" ([abstract, §1, §3.1](https://arxiv.org/abs/2411.15100)). It also sorts tokens lexicographically so tokens that share a prefix (such as "read", "ready" and "reader") are not re-checked from scratch ([§3.3](https://arxiv.org/abs/2411.15100)).
- DOMINO identifies "token misalignment" with CFG terminals and proposes "minimally invasive" constraining ([§1–§2](https://arxiv.org/abs/2403.06988)).
- Geng et al. frame grammar-constrained decoding as an alternative to fine-tuning, "a rapid and cost-effective adaptation strategy that enables LMs to produce reliable structured outputs without the need for fine-tuning" ([Appendix A, "Fine-tuning vs. GCD"](https://arxiv.org/abs/2305.13971)). This is relevant to the panel's "will it be fine-tuned" question: masking and fine-tuning are separate mechanisms.

## 4. Finite automaton vs pushdown automaton

A pushdown automaton is a finite automaton plus a stack alphabet Γ, with transitions that read and write the stack ([Outlines, Definition 2](https://arxiv.org/abs/2307.09702), after Sipser). Outlines uses PDAs "as a means to extend the FSM approach" to CFGs ([§4](https://arxiv.org/abs/2307.09702)). "All regular languages can be recognized by a nondeterministic finite automata" ([DOMINO, §3.1](https://arxiv.org/abs/2403.06988)). A CFG's "recursive nature provides greater expressive power than … regular expressions", and interpreting it "requires a stack state that tracks the recursive rules matched so far". Because "the unbounded stack length results in an infinite number of possible states", masks cannot all be precomputed ([XGrammar, §1, §2.2](https://arxiv.org/abs/2411.15100)).

The INTERCEPT line is one of two fixed strings, then a space, a capital letter, 5–98 characters from a fixed set, and `?`. Nothing nests, and the bounded repeat `{5,98}` only needs a counter that stops at 99. That is why `("question", n)` is a finite set of states and the whole automaton has 193 of them. General JSON allows objects inside arrays inside objects to any depth, and matching each closing bracket to its opener needs a stack. llama.cpp therefore runs every grammar as pushdown stacks (§3).

My inference, not verified: INTERCEPT_SCHEMA is a flat object of two strings, so the GBNF converted from it probably has no recursive rule. If so, the language LM Studio enforces is regular even though the engine is a PDA. I did not inspect the converted grammar.

## 5. Known limits

- **Structure, not meaning.** Outlines promises "guaranteeing the structure of the generated text" ([abstract](https://arxiv.org/abs/2307.09702)), and no source read claims more. ADR 0004 records a grammatical but leading probe line, "It's a nightmare, isn't it?" ([ADR 0004](../../docs/adr/0004-intercept-constrained-decoding-via-lm-studio.md)).
- **Distortion of the model's distribution.** Constrained decoding "can distort the LLM's distribution, leading to outputs that are grammatical but appear with likelihoods that are not proportional to the ones given by the LLM" ([Park et al., abstract](https://arxiv.org/abs/2405.21047)). DOMINO shows that naive constraining makes the output "diverge from the unconstrained case": accuracy on JSON-formatted GSM8K fell from 41.5% to 30.8% ([§2](https://arxiv.org/abs/2403.06988)). Geng et al. call this "likelihood misalignment": "the structure imposed by the grammar may be unnatural to the model, especially when the model is not finetuned on the respective task" ([§5](https://arxiv.org/abs/2305.13971)).

  The trace shows this. At step 1, greedy decoding took `" notice"` (p = 0.12) because `" understand"` (0.75) was blocked. At step 2 the mask removed probability 1.000 and left 2 tokens, forcing `"d"`. The text "I noticed" is right, but it arrived as `"I" + " notice" + "d"` even though Gemma's tokenizer has the single token `"▁noticed"` (id 14275, checked in the cached `tokenizer.json`). Geng et al. note that the same string can be tokenized several ways (their `"[[["` example, §2.1). Step 11 removed probability 1.000 too (the model wanted `"\n\n"`).

  DOMINO says regex-based decoding "typically does not suffer from the token misalignment problem". The character-level automaton fits that: it does allow boundary-crossing tokens such as `" What"`. What the trace shows is the distortion Park et al. describe, not misalignment.
- **Dead ends.** Grammar-constrained decoding is meant to mask any token that leads to "a prefix w1:i for which no completion will produce a sequence in the grammar" ([Park et al., §2](https://arxiv.org/abs/2405.21047)). If a checker lets a dead prefix through, a later step has nothing left to allow. transformers raises "the constraint is unsatisfiable" on an empty allowed list ([L1387–L1394](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/logits_process.py#L1387-L1394)), and llama.cpp throws "Unexpected empty grammar stack" ([L1472](https://github.com/ggml-org/llama.cpp/blob/ff5a23376725e5a889fa0bfb987b7541dc304da0/src/llama-grammar.cpp#L1472)).

  The student's `step` returns `None` the moment a prefix cannot be completed (`test_dead_as_soon_as_a_prefix_cannot_be_completed`). That leaves one possible gap: a live state with no token that fits. I checked the Gemma tokenizer and it has a single-character piece for every character the grammar uses, plus 256 byte-fallback pieces, so that cannot happen with this vocabulary. `MaskingLogitsProcessor` still raises `RuntimeError` if the allowed set is ever empty.
- **`max_new_tokens` truncation.** `max_new_tokens` is "the maximum numbers of tokens to generate" ([configuration_utils.py L136–L137](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/configuration_utils.py#L136-L137)). Outlines' Algorithm 2 stops on EOS or after L steps, whichever comes first ([§2.2](https://arxiv.org/abs/2307.09702)). Masking keeps every prefix live but does not make the line finish within the token budget. The longest valid line is 48 + 1 + 100 = 149 characters, and the trace script allowed 60 tokens; the masked line used 26 steps. A truncated line is a valid prefix, which the regex check rejects, so it would go to the fallback.
- **Latency.** Geng et al. list the added latency as a limitation, and it grows with grammar size. Their CPU parser's overhead was 1–69 ms per token depending on the task ([§4.4, Table 4; Limitations](https://arxiv.org/abs/2305.13971)). The trace recorded 29.01 s masked against 15.37 s unmasked ([run record](token_masking_2026-10-18/token_masking_2026-10-18.run_record.json)). The difference includes the trace's own softmax and top-k bookkeeping and was not measured separately.

## 6. Concept → code → source

| Concept | Student's code | Primary source | Simpler than / deviates from the source? |
|---|---|---|---|
| Line grammar as a regex | `grammar_decoder._QUESTION`, `_GRAMMAR["INTERCEPT"]` | Outlines §3 | Same idea. A test checks the automaton against the regex on 3,000 random lines |
| Finite automaton (Q, Σ, δ, q0, F) | `InterceptAutomaton.start`, `.step`, `.is_accepting` | Outlines Def. 1 | Hand-written, not compiled from the regex. Fine for one grammar, but it must be kept in step with the regex (the test does this) |
| Dead state = prefix with no completion | `step` returns `None` | Park et al. §2 (prefix language) | Matches |
| Track the state between tokens | `TokenMask.state_after` | Outlines §3 | **Simpler.** It re-runs the automaton from the start of the line every step, the cost Outlines avoids |
| Token allowed iff automaton survives all its characters | `TokenMask.allowed` → `automaton.run(text, state)` | Outlines Alg. 3; llama.cpp L1061–L1130 | Matches |
| Allowed set per step | `TokenMask.allowed`, first-character buckets `_by_first` | Outlines §1 (O(N)) vs index (Alg. 4); XGrammar §3.3 | **Simpler.** It scans the vocabulary every step instead of precomputing `σ: Q → P(V)`. The buckets are a one-level version of llama.cpp's first-code-point filter and XGrammar's shared-prefix checking. A precomputed index is feasible here because Q has only 193 states |
| Token piece → text | `piece_text` (`▁` → space, `<0xNN>` → character) | llama.cpp `token_to_piece` + `decode_utf8` with `partial_utf8` | **Deviation.** Bytes ≥ 0x80 become single Latin-1 characters rather than partial UTF-8. That is harmless only because the grammar is ASCII, so those tokens are always rejected. It would be wrong for a non-ASCII grammar |
| Special tokens never allowed | `texts[i] = None` for specials | llama.cpp: empty piece → `-INFINITY` | Matches |
| EOS only in accepting state | `end_ids` added only when `is_accepting` | Outlines §2.1; llama.cpp `allow_eog` | Matches |
| Mask = scores of disallowed tokens → −∞ | `MaskingLogitsProcessor.__call__` | XGrammar §2.1; transformers `PrefixConstrainedLogitsProcessor` | Matches |
| Empty allowed set is an error | `RuntimeError("no token can continue …")` | transformers `ValueError` "constraint is unsatisfiable" | Matches |
| Hook into `generate` | `LogitsProcessorList([processor])` in `trace_token_masking.py` | transformers `LogitsProcessor` docs and source | **Minor deviation.** It does not subclass `LogitsProcessor` (it works because `LogitsProcessorList` just calls `processor(input_ids, scores)`, [L83–L93](https://github.com/huggingface/transformers/blob/v4.53.2/src/transformers/generation/logits_process.py#L83-L93)). It handles batch size 1 only (`input_ids[0]`) and no beams |
| Record raw vs masked choices | `trace` (top-k before masking, blocked probability) | Outlines §5 suggests quantifying "the discrepancy between the masked logits … and the raw logits" | An addition for evidence, not part of the published systems |
| Child-facing masking | `_intercept` → `response_format` JSON schema | llama.cpp JSON Schema → GBNF (README L141–L212) | Different engine (PDA, as above). ADR 0004 |

Nothing in `token_mask.py` contradicts how the sources define masking. The differences are that it is simpler: it recomputes per step, re-runs from the start, uses one level of bucketing, handles batch 1 only, and assumes ASCII bytes. That is acceptable for a demonstration trace that is not on the child-facing path.

## What I could not verify

- **The LM Studio engine build.** The llama.cpp code cited here is upstream commit `ff5a233`, not the build bundled in LM Studio (the saved logs name `llama.cpp-win-x86_64-nvidia-cuda-avx2@1.46.0`; see the 18 Oct note). The mechanism is very likely the same, but line-level details may differ.
- **The GBNF generated from INTERCEPT_SCHEMA.** I did not inspect it, so the claim in §4 that it is non-recursive is an inference.
- **Sampler order in llama.cpp.** I did not check where the grammar sampler sits in llama.cpp's sampler chain, for example before or after top-k.
- **The current Outlines library.** I read only the 2023 paper, not the library's code, which may since have changed internally.
- **Papers I did not read.** These are cited inside the papers above but were not read: Synchromesh, PICARD, Kuchnik et al. (ReLM), Deutsch et al. 2019.
- **Out of scope.** Gemma 3 1B's parameter count and fine-tuning are not covered here. The only relevant point is that masking changes no weights ([Geng et al.](https://arxiv.org/abs/2305.13971): constraints "without finetuning").
- **The masked-run overhead.** How much of the 13.6 s extra time came from the mask and how much from trace bookkeeping was not measured.
